## Coordinate-origin finding changes the validation order

The current client rounds `XYZ/250` as zero-based voxel-center indices. The deposited Gou atlas code defines physical centers using `(Julia_index - 0.5) * 250` and samples with `ceil(XYZ/250)` in Julia one-based indices. Dividing coordinates by the resolution alone does not resolve this half-voxel origin difference. The current client also uses ties-to-even rounding, whereas the new map kernels declare half-open center cells; those agree away from exact half-index ties.

The [independent sensitivity audit](../atlas_locations/soma_audit_20261009/coordinate_origin_uncertainty_20261009.md) keeps the same local ARM6 and compares policies without changing any label. Among 1,912 available own-source roots, the deposited edge-origin policy changes 227 labels; among 8,409 portal-coordinate records, it changes 819. All assessed hemispheres remain the same. The center-cell tie policy changes one label (`252383/064.swc`). These are policy sensitivity results, not evidence that either policy is correct for the portal exports. The paper's original v2.0 CHARM/SARM differs from the v2.1 ARM used in this isolated comparison.

For 251637/112 and /114, the current lookup is background and the edge-origin alternative is `CR_Ia/Id`; both are R under every policy. The reviewed 112 R-IDM and user-selected provisional 114 R-IDM remain intact. Neither alternative resolves the fine parcel. Recover the actual SWC export origin, reference/atlas version, sample transform and local landmark QC before accepting fine localization or running a new anatomically interpreted terminal map. Existing length maps remain preserved as demonstrations under their recorded coordinate assumption.
